## เชื่อมงานกับทีม — RM-24

| ส่วนงาน | ส่งต่ออะไรให้ส่วนคำขอ | สิ่งที่ต้องคงไว้ |
| --- | --- | --- |
| บัญชี/โปรไฟล์ | token จาก login/register และ userId ของผู้ใช้ปัจจุบัน | ใช้ token ของผู้ทำรายการจริง; เปลี่ยนบัญชีต้องไม่ใช้ token เก่า |
| ห้องพัก | roomId จาก create/list/detail และสถานะ/ที่ว่างปัจจุบัน | นับเฉพาะผู้พักจริง; pending ยังไม่ใช่การจอง; อย่าลบประกาศอัตโนมัติเมื่อเต็ม |
| คำขอ/สมาชิก/เพื่อน | requestId จากคำขอ, connectionId จากคำชวน | อย่าสลับ ID ทั้งสองชนิด หรือใช้การเป็นเพื่อนแทนสิทธิ์สมาชิกห้อง |

- JSON API ใช้ ID เป็น **number** และส่งเวลาตอบกลับเป็น ISO 8601 UTC ส่วน `src/lib/api.ts`
  แปลง ID เป็น string ให้ frontend และแปลง recipientId ของคำชวนกลับเป็น number
- ใช้ `api.createJoinRequest`, `mineRequests`, `ownerRequests`, `requesterProfile`,
  `decideRequest`, `cancelRequest` ของ adapter เดิม ไม่ต้องสร้าง fetch/token handling ซ้ำ
- `401` ให้ระบบบัญชีจัดการ session; `403` คือไม่มีสิทธิ์ ไม่ใช่ให้ logout;
  `409` ให้โหลดสถานะล่าสุดก่อนลองใหม่; network/`5xx` ให้แสดง error และทางลองใหม่
  ข้อความ error อาจเป็นภาษาไทยหรืออังกฤษ อย่าใช้ข้อความเป็นตัวตัดสินสิทธิ์
- หลังอนุมัติ/ปฏิเสธให้อัปเดต `OwnerRequestsContext` เพื่อให้รายการและจุดแจ้งเตือนตรงกัน
  จุดแสดงจำนวนงาน pending ไม่ใช่สถานะอ่านแล้ว และการเปิดหน้าไม่ทำให้จุดหาย
- ฟิกซ์เจอร์ห้องใหม่ต้องผ่าน validation ที่รวมจาก `feature/listing-validation` แล้ว:
  ราคาเป็นจำนวนเต็มมากกว่า 0, priceBasis, locality, map URL สมบูรณ์ และรูปอย่างน้อย 1 รูป
  ใช้รูปที่อัปโหลดโดยเจ้าของตาม [UPLOADS.md](UPLOADS.md) หรือ URL เดิมที่รองรับ;
  seed/รายงาน QA เก่าอาจมีห้องไม่มีรูป จึงไม่ควรคัดลอก payload เก่ามาสร้างห้องใหม่

### Curl setup

ตัวอย่างต่อไปใช้ `RM_API=http://127.0.0.1:3001/api` ตาม API dev ปกติ
หากใช้ฐาน QA ให้เปลี่ยนเป็น URL ที่เปิดไว้ ตัวแปร token รับจาก login ของแต่ละบทบาท
และเก็บเฉพาะ session ทดสอบในเครื่อง ไม่ใส่ token จริงลง Git หรือเอกสาร
ID/ชื่อ/เวลาใน JSON ตัวอย่างมีไว้แสดงรูปแบบ ให้ใช้ค่าที่ API คืนจริงเสมอ

```bash
export RM_API='http://127.0.0.1:3001/api'
```

| ตัวแปร | ค่า |
| --- | --- |
| `RM_API` | base URL ที่ลงท้าย `/api` |
| `RM_OWNER_TOKEN`, `RM_APPLICANT_TOKEN` | token เจ้าของห้อง / ผู้ขอ |
| `RM_ROOM_ID` | roomId ของห้องที่เปิดรับและมีที่ว่าง |
| `RM_REQUEST_ID` | requestId จากผลส่งคำขอ ไม่ใช่ roomId |

ส่งคำขอด้วยบัญชีผู้ขอ ไม่ต้องส่ง userId หรือ ownerId ใน body:

```bash
curl -sS -X POST "$RM_API/rooms/$RM_ROOM_ID/requests" \
  -H "Authorization: Bearer $RM_APPLICANT_TOKEN"
```

ตัวอย่างผล `201`:

```json
{
  "request": {
    "requestId": 42,
    "status": "pending",
    "requestedAt": "2026-11-15T10:00:00.000Z",
    "respondedAt": null,
    "membershipActive": false,
    "room": { "roomId": 10, "title": "ห้องทดสอบ" },
    "requester": { "userId": 2, "firstName": "เอ", "lastName": "ทดสอบ", "profileImage": null }
  }
}
```

เจ้าของอ่านคำขอแล้วอนุมัติด้วย token เจ้าของ:

```bash
curl -sS "$RM_API/owner/requests" -H "Authorization: Bearer $RM_OWNER_TOKEN"
```

```bash
curl -sS -X PATCH "$RM_API/requests/$RM_REQUEST_ID" \
  -H "Authorization: Bearer $RM_OWNER_TOKEN" -H 'Content-Type: application/json' \
  --data '{"status":"approved"}'
```

ผล `200` มี `request` ที่เป็น approved และ `match` ตาม [MATCHES.md](MATCHES.md)
หากปฏิเสธใช้ `status: rejected` และผลจะไม่มี key `match`
ถอนใช้ requestId ของรายการที่ยัง pending เท่านั้น ตัวอย่างนี้เป็นอีกทางเลือกก่อนเจ้าของตัดสินใจ:

```bash
curl -sS -X POST "$RM_API/requests/$RM_REQUEST_ID/cancel" \
  -H "Authorization: Bearer $RM_APPLICANT_TOKEN"
```

## API contract

ทุก endpoint ต้องส่ง `Authorization: Bearer <token>` จากระบบบัญชีของคนที่ 1
ห้ามเชื่อ `userId` หรือ `ownerId` ที่ client ส่งมาเพื่อกำหนดสิทธิ์

| Method / URL | ผู้ใช้ | Request body | ผลสำเร็จ |
| --- | --- | --- | --- |
| `POST /api/rooms/:roomId/requests` | ผู้ขอเข้าพัก | ไม่ต้องมี body | `201 { request }` |
| `GET /api/requests/mine` | เจ้าของบัญชี | ไม่มี | `200 { requests: [...] }` |
| `GET /api/owner/requests` | เจ้าของประกาศ | ไม่มี | `200 { requests: [...] }` |
| `POST /api/requests/:requestId/cancel` | ผู้ส่งคำขอ | ไม่มี | `200 { request }` |
| `GET /api/requests/:requestId/profile` | เจ้าของห้องของคำขอนั้น | ไม่มี | `200 { profile }` |
| `PATCH /api/requests/:requestId` | เจ้าของห้องของคำขอนั้น | `{ "status": "approved" }` หรือ `{ "status": "rejected" }` | `200 { request, match? }` |

`request` ประกอบด้วย:

- `requestId`, `status`, `requestedAt`, `respondedAt`, `membershipActive`
- `room: { roomId, title }`
- `requester: { userId, firstName, lastName, profileImage }`

สถานะเริ่มต้นเป็น `pending` และ `respondedAt` เป็น `null`
เมื่อเจ้าของตัดสินใจแล้ว จะเป็น `approved` หรือ `rejected` พร้อมเวลาตอบกลับ
ตัวอย่างเวลา: `2026-11-12T03:00:00.000Z` ให้ frontend แปลง timezone ตอนแสดงผล
การอนุมัติส่ง `match` กลับตาม contract เดิม การปฏิเสธไม่มี key `match`
ไม่มีคำขอให้ส่ง `{ "requests": [] }` ไม่ใช่ error

ถอน pending ได้ด้วย endpoint cancel: สถานะเป็น `cancelled` พร้อม `respondedAt`
เก็บประวัติ ส่งใหม่ได้ และเรียกถอนซ้ำได้โดยไม่เปลี่ยนเวลาเดิม final อื่นตอบ 409
`membershipActive` บอกสมาชิกปัจจุบัน แยกจากคำขออนุมัติในประวัติหลังออกจากห้อง
รายละเอียด migration และ UI อยู่ [UX_FIXES.md](UX_FIXES.md)

### สถานะที่ frontend ต้องแยก

| สถานะคำขอ | ผลกับห้อง | สิ่งที่ผู้ใช้ทำต่อได้ |
| --- | --- | --- |
| `pending` | ไม่กินที่ว่าง และไม่สร้างสมาชิก/แมตช์ | ผู้ส่งถอน; เจ้าของอนุมัติเมื่อเปิดรับและมีที่ว่าง หรือปฏิเสธ |
| `approved` | สร้าง/เปิดสมาชิกและแมตช์ใน transaction เดียว | ดูสมาชิก/ติดต่อ หรือออกจากห้องผ่าน member API |
| `rejected` | ไม่เพิ่มสมาชิก/แมตช์ | ส่งคำขอใหม่ได้เมื่อห้องเปิดรับและมีที่ว่าง โดยใช้ requestId ใหม่ |
| `cancelled` | ไม่เพิ่มสมาชิก/แมตช์ เก็บเวลาถอนเดิม | ผู้ส่งถอนซ้ำได้แบบ idempotent หรือส่งคำขอใหม่เมื่อห้องรับอยู่ |

`membershipActive` เป็นสถานะสมาชิก **ปัจจุบันของคู่ผู้ใช้–ห้อง** ไม่ใช่สถานะของคำขอแถวนั้น
คำขอเก่า approved ยังเป็นประวัติหลังออก; หากสมัครใหม่และอนุมัติอีกครั้ง ค่านี้อาจเป็น true
ในประวัติเดิมด้วย ห้ามนับจำนวนสมาชิกจากจำนวนคำขอ approved หรือเปลี่ยนคำขอเป็น `left`
เมื่อผู้ใช้ออก ให้ใช้ `/members`, `room.memberCount`, `availableSlots` และ member API แทน

### Error contract

ทุกข้อผิดพลาดเป็น JSON `{ "error": "ข้อความ" }`:

RM-18 แยกเหตุผล `409` ให้ตรงสถานะจริง: ตรวจห้องตนเอง สมาชิกเดิม และคำขอ pending
ที่มีอยู่ก่อนตรวจความพร้อมห้อง จึงไม่บอกสมาชิกเดิมว่า “ห้องเต็ม” หรือผู้ที่มีคำขอ
อยู่แล้วว่า “พักประกาศ” ถ้าผู้ใช้ยังไม่มีสมาชิก/คำขอ จึงแยกพักประกาศ (`Inactive
rooms cannot accept requests`) กับเต็ม (`This room has no available place`)
HTTP status และโครงสร้าง JSON เดิมยังคงเดิม ไม่มีการเปลี่ยนฐานข้อมูล
frontend แปลเหตุผลและสิทธิ์ของผู้ขอ/เจ้าของเป็นภาษาไทยผ่าน `friendlyApiError`
ส่วนคำชวนยังใช้ข้อความไทยเฉพาะเหตุการณ์เดิม กรณี 409 ที่ไม่รู้จักใช้ข้อความกลาง
เกี่ยวกับสถานะรายการ โดยไม่อ้างเรื่องที่ว่างของห้องกับคำชวนเพื่อน
`ApiError` แปลข้อความตั้งแต่ตอนสร้าง error เพื่อให้เส้นทาง session หมดอายุของ
ระบบบัญชีที่รวมจาก main ยังแสดงภาษาไทย โดยไม่เปลี่ยน status หรือการแจ้ง session
และไม่ต้องแก้/ทับขั้นตอนจัดการ token ของเพื่อน

การตรวจ RM-18 ชุดแรก: tests ตรวจลำดับเหตุผล 409 และยืนยันว่าไม่เพิ่ม/เปลี่ยนแถว
จากคำขอที่ถูกปฏิเสธ, ทดสอบ API adapter จริงหลังแปลง TypeScript ด้วย Vite,
รวมการส่งข้อความไทยซ้ำและการแจ้ง session หมดอายุ ตรวจสำเนา main `fbd3bce`
พร้อมชุดแก้นี้ผ่าน `npm test` 116 ข้อและ build ผ่าน โดยรักษาโค้ดบัญชีของเพื่อน
Browser กับฐานข้อมูลแยกตรวจห้องเต็ม พักประกาศ ส่งซ้ำ สมาชิกเดิม และ API 503
ที่มีข้อความภายใน แล้ว refresh ตรวจข้อมูลอนุมัติยังอยู่ (desktop 1440×900,
tablet 820×1000, mobile 320×740) ชุด UI ของ RM-18 ต่อจากชุดนี้อัปเดตป้ายสถานะหลัง 409
และเพิ่มคำแนะนำขั้นตอนถัดไปบนการ์ดคำขอแล้ว

- `400`: ID ไม่เป็นจำนวนเต็มบวกที่ปลอดภัย, JSON ผิดรูปแบบ, status ไม่ใช่ approved/rejected
- `401`: ไม่มี token, token ไม่ถูกต้อง/หมดอายุ หรือบัญชีเข้าใช้งานไม่ได้
- `403`: ผู้ตอบไม่ใช่เจ้าของห้อง แม้เป็นผู้ส่งคำขอเองก็ตอบแทนไม่ได้
- `404`: ไม่พบห้องหรือคำขอ
- `409`: ห้องตนเอง, มีคำขอ pending ซ้ำ, ห้องเต็ม/พักประกาศ, เป็นสมาชิกแล้ว,
  เป็นสมาชิกอยู่ หรือคำขอถูกตัดสิน/ถอนไปแล้ว
- `500`: ข้อผิดพลาดที่ไม่คาดคิด เช่น เขียนฐานข้อมูลไม่ได้ client ไม่ได้รับ stack trace/SQL

รายการ `mine` ต้องมีเฉพาะคำขอของบัญชีที่ล็อกอิน รายการ `owner` ต้องมีเฉพาะห้อง
ที่บัญชีนั้นเป็นเจ้าของ ไม่ส่ง email, phone, password hash หรือช่องทางติดต่อใน requester

### ดูโปรไฟล์ผู้ขอเข้าพัก

ปุ่ม **ดูโปรไฟล์** ในแท็บคำขอถึงฉัน เปิดหน้าต่างย่อยผ่าน
`GET /api/requests/:requestId/profile` โดยตรวจสิทธิ์เจ้าของห้องจากคำขอจริง
ผู้ส่งคำขอเอง ผู้ใช้ทั่วไป และเจ้าของห้องอื่นใช้ endpoint นี้ไม่ได้ (`403`)

`profile` มีเฉพาะ `userId`, `firstName`, `lastName`, `profileImage`, `university`,
`bio`, `lifestyle`, `budgetMin`, `budgetMax` ข้อมูลเป็นค่าปัจจุบัน ณ เวลาเปิดดู
ใช้ข้อมูลชุดเดียวกับโปรไฟล์สาธารณะของหน้าหาเพื่อน ไม่มีช่องทางติดต่อ วันเกิด หรือเพศ
ช่องที่ยังไม่กรอกคืน `null` และ frontend แสดงข้อความว่าไม่ได้ระบุ

อ่านได้ทั้งคำขอ pending/approved/rejected ของห้องตนเอง หากผู้ขอ inactive
หรือไม่พบคำขอคืน `404` ไม่มี token/บัญชีเจ้าของ inactive คืน `401`
ID ตัวเลขที่ไม่เป็น positive safe integer คืน `400` ข้อผิดพลาดฐานข้อมูลคืน
`500 { "error": "Internal server error" }` โดยไม่มีรายละเอียด SQL

การเปิดโปรไฟล์ไม่อนุมัติคำขอ ไม่สร้างสมาชิกหรือแมตช์ และไม่เปิดเผยข้อมูลติดต่อ
แม้คำขอนั้นได้รับอนุมัติแล้ว ช่องทางติดต่อยังใช้หน้าสมาชิก/แมตช์ตาม flow เดิม
ไม่เปลี่ยน schema และไม่เปลี่ยน response ของรายการคำขอเดิม

ไฟล์ส่วนนี้: `server/requests.js`, `src/lib/api.ts`, `src/pages/RequestsPage.tsx`,
`src/components/RequesterProfileModal.tsx`, `src/components/RequesterProfileModal.css`,
`tests/requests.test.mjs` และเอกสารนี้

## กฎและความถูกต้องของข้อมูล

- ห้ามขอเข้าห้องตัวเอง ห้อง inactive หรือห้องที่ไม่มีที่ว่าง
- คำขอ pending ไม่ใช่การจองที่ อาจมีหลายคนรอที่ว่างเดียวกัน
- ที่ว่าง = capacity - จำนวนสมาชิก approved - (ผู้ลงประกาศพักด้วย ? 1 : 0) ดู [กติกาจำนวนผู้พัก](ROOM_OCCUPANCY.md)
- การส่งคำขอตรวจห้อง/สมาชิก/คำขอซ้ำและ INSERT ภายใน transaction และล็อกห้องด้วย `SELECT ... FOR UPDATE`
- การอนุมัติตรวจสิทธิ์ สถานะ และความจุอีกครั้งใน transaction เดียว แล้วจึง:
  1. เปลี่ยนคำขอเป็น approved และกำหนดเวลาตอบ
  2. เพิ่ม/เปิดใช้งาน `ROOM_MEMBER` เดิมกรณีเคยออกจากห้อง
  3. เพิ่ม/ปรับเวลา `MATCHES` ระหว่างเจ้าของกับผู้ขอสำหรับห้องนั้นโดยไม่สร้างคู่ซ้ำ
  4. เปลี่ยนห้องเป็น full เมื่อครบความจุ (รวมถึง triggers เดิมของฐานข้อมูล)
- ถ้าขั้นตอนใดล้มเหลวต้อง rollback ทั้งหมด รวมถึงสถานะ full ที่เปลี่ยนจาก trigger
- การปฏิเสธไม่สร้างสมาชิกหรือแมตช์ และทำได้แม้ห้องเต็ม/พักประกาศแล้ว
- คำขอที่ตัดสินแล้วห้ามแก้ผล ถ้าถูกปฏิเสธผู้ขอส่งคำขอใหม่ได้เมื่อห้องยังรับอยู่
  โดยเก็บประวัติเดิมและใช้ `requestId` ใหม่
- ถ้าสองคำขอแย่งที่ว่างสุดท้าย อนุมัติได้เพียงคนเดียว อีกคำขอยังคง pending
  เจ้าของสามารถปฏิเสธคำขอที่เหลือได้ ระบบยังไม่ปฏิเสธให้อัตโนมัติ
- ถอนคำขอ pending ได้; ยังไม่มีคำขอแบบกลุ่มหรือการหมดอายุอัตโนมัติ

## ทดสอบอัตโนมัติ

```bash
node --test tests/requests.test.mjs
npm test
npm run build
```

Tests ใช้ HTTP server จริงบนพอร์ตสุ่มและฐานข้อมูลแยก ไม่แตะฐานข้อมูลส่วนตัว
ครอบคลุม auth, การแยกบัญชี, การปลอม userId, คำขอซ้ำ, input ผิด,
อนุมัติ/ปฏิเสธ, ประวัติการส่งใหม่, ห้องเต็ม/พักประกาศ, สอง request แข่งกัน,
ฐานข้อมูลเขียนไม่ได้, trigger ล้มเหลวระหว่างอนุมัติ และหยุด/เปิด API ใหม่กับ SQLite เดิม
การทดสอบ concurrency นี้เป็นคำขอพร้อมกันใน Node process เดียว ไม่ใช่ load test หลายเครื่อง

## Checklist ให้เจ้าของฟีเจอร์ลองผ่านเว็บก่อน commit

ผลตรวจรับด้วยเจ้าของห้องและผู้ขอ 2 คน พร้อม empty/invalid/failure/persistence
และวิธีเปิดฐาน QA แยกสำหรับทีม: [RM-16 acceptance](RM16_ACCEPTANCE.md)

1. เปิดเว็บด้วย `npm run dev` ตาม README ใช้บัญชีเจ้าของห้อง A และผู้ขอ B
   ใน browser profile แยกกันหรือ private window
2. B เปิดห้องที่มีที่ว่าง แล้วกดขอเข้าพัก ปุ่มต้องกลายเป็นรอพิจารณา
3. B เปิดหน้าคำขอเข้าพักและ refresh ต้องเห็นรายการเดิม
4. A เปิดหน้าคำขอเข้าพัก/refresh แล้วอนุมัติ ตรวจว่า B เป็นสมาชิกและที่ว่างลดลง
5. ทดลองอีกห้องแล้วปฏิเสธ ต้องไม่มีสมาชิก/แมตช์จากคำขอนั้น
6. B ลองส่งใหม่หลังถูกปฏิเสธ ต้องมีรายการใหม่โดยประวัติเดิมยังอยู่
7. ทดสอบหน้าจอ desktop/mobile และลองคำขอมากกว่าที่ว่างของห้อง

ส่วนโปรไฟล์ผู้ขอตรวจด้วย API tests/build และ browser จริงบน desktop/mobile
รวมข้อมูลว่าง รูปโหลดไม่ได้ ข้อความยาว การปิดระหว่างโหลด การลองใหม่ และโปรไฟล์ inactive

การเพิ่มถอนคำขอและ migration ในรอบ UX ล่าสุดอยู่ใน [UX_FIXES.md](UX_FIXES.md)
ไม่มีการ commit, push, เปลี่ยน branch หรือย้ายงานของเพื่อนเข้ามา
เจ้าของฟีเจอร์ตรวจ diff และเป็นผู้ commit เองเมื่อพร้อม


### RM-18: หน้าจอตามสถานะล่าสุด

- ส่งคำขอแล้วได้ 409: ดึงรายละเอียดห้องใหม่ เพื่ออัปเดตป้ายเต็ม/พักประกาศ ที่ว่าง สมาชิก และคำขอเดิม พร้อมแสดงเหตุผลจริงจาก API
- หากดึงสถานะไม่สำเร็จ ปิดปุ่มส่งคำขอไว้และให้กด **อัปเดตสถานะห้อง** ก่อนส่งใหม่
- เจ้าของตัดสินใจแล้วได้ 409: อัปเดตคำขอและที่ว่าง แยกข้อความเต็มกับพักประกาศ ปิดปุ่มเมื่อคำขอถูกจัดการแล้ว และมีปุ่มลองใหม่หากตรวจคำขอไม่ได้
- ผู้ขอถอนแล้วได้ 409: อัปเดตรายการที่ส่งและสถานะในหน้าต่างเดิม ปิดปุ่มถอนหากได้รับอนุมัติ/ถูกจัดการแล้ว โดยไม่แสดงว่าถอนสำเร็จ
- การ์ดอนุมัติบอกทางไปดูสมาชิก/ติดต่อ การ์ดไม่อนุมัติบอกว่าสามารถเลือกห้องอื่นหรือส่งใหม่เมื่อเปิดรับ
- ข้อผิดพลาดรับ keyboard focus และเมื่อปิดหน้าต่างที่คำขอไม่ pending แล้ว จะคืน focus ไปแท็บที่เกี่ยวข้อง

ตรวจด้วย browser บนฐานข้อมูล QA แยกจากข้อมูลใช้งาน: desktop 1440×900,
tablet 820×1000, mobile 390×844 และ 320×740 รวมกรณีส่ง/ถอนปกติ,
ที่ว่างสุดท้ายถูกอนุมัติจากอีกหน้า, พักประกาศ, ถอนชนกับอนุมัติ,
คำขอถูกจัดการระหว่างเปิดหน้าต่าง และ GET สถานะตอบ 503 แล้วลองใหม่
ไม่มีการเปลี่ยน schema หรือ API contract ในชุด UI นี้
