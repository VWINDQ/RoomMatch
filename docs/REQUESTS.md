# ขอเข้าพัก — โมดูลที่ 3 / ฟีเจอร์แรก

เอกสารนี้ครอบคลุมเฉพาะการส่งคำขอ ดูสถานะ และการอนุมัติ/ปฏิเสธ
ไม่รวมการพัฒนาหน้าแมตช์/สมาชิกหรือหาเพื่อนเพิ่มเติม

## ไฟล์และขอบเขตงาน

- `server/requests.js`: routes, validation, การอ่านคำขอ และ transaction ของคำขอ
- `server/app.js`: เชื่อมโมดูลเข้ากับ HTTP server และใช้ authentication/error handling เดิม
- `tests/requests.test.mjs`: เรียก HTTP API จริงกับฐานข้อมูลทดสอบแยก
- UI เดิมใช้ `src/pages/RequestsPage.tsx`, ปุ่มใน `RoomDetailPage.tsx` และ `src/lib/api.ts`
  โดยรอบนี้ไม่ได้แก้ไฟล์ frontend หรือ schema

ระบบมี API เบื้องต้นอยู่ก่อนแล้ว รอบนี้แยกเฉพาะฟีเจอร์ออกจาก `app.js`
เพื่อให้เพื่อนที่ทำบัญชีและห้องไม่ต้องแก้ logic คำขอในไฟล์เดียวกัน
คง URL, ชื่อฟิลด์ และรูปแบบ response เดิม เพิ่มการตรวจ ID ให้เป็น positive safe integer
และใช้เวลา `respondedAt` แบบ ISO 8601 UTC ที่มี `Z` เหมือน `requestedAt`

## API contract

ทุก endpoint ต้องส่ง `Authorization: Bearer <token>` จากระบบบัญชีของคนที่ 1
ห้ามเชื่อ `userId` หรือ `ownerId` ที่ client ส่งมาเพื่อกำหนดสิทธิ์

| Method / URL | ผู้ใช้ | Request body | ผลสำเร็จ |
| --- | --- | --- | --- |
| `POST /api/rooms/:roomId/requests` | ผู้ขอเข้าพัก | ไม่ต้องมี body | `201 { request }` |
| `GET /api/requests/mine` | เจ้าของบัญชี | ไม่มี | `200 { requests: [...] }` |
| `GET /api/owner/requests` | เจ้าของประกาศ | ไม่มี | `200 { requests: [...] }` |
| `PATCH /api/requests/:requestId` | เจ้าของห้องของคำขอนั้น | `{ "status": "approved" }` หรือ `{ "status": "rejected" }` | `200 { request, match? }` |

`request` ประกอบด้วย:

- `requestId`, `status`, `requestedAt`, `respondedAt`
- `room: { roomId, title }`
- `requester: { userId, firstName, lastName, profileImage }`

สถานะเริ่มต้นเป็น `pending` และ `respondedAt` เป็น `null`
เมื่อเจ้าของตัดสินใจแล้ว จะเป็น `approved` หรือ `rejected` พร้อมเวลาตอบกลับ
ตัวอย่างเวลา: `2026-11-12T03:00:00.000Z` ให้ frontend แปลง timezone ตอนแสดงผล
การอนุมัติส่ง `match` กลับตาม contract เดิม การปฏิเสธไม่มี key `match`
ไม่มีคำขอให้ส่ง `{ "requests": [] }` ไม่ใช่ error

### Error contract

ทุกข้อผิดพลาดเป็น JSON `{ "error": "ข้อความ" }`:

- `400`: ID ไม่เป็นจำนวนเต็มบวกที่ปลอดภัย, JSON ผิดรูปแบบ, status ไม่ใช่ approved/rejected
- `401`: ไม่มี token, token ไม่ถูกต้อง/หมดอายุ หรือบัญชีเข้าใช้งานไม่ได้
- `403`: ผู้ตอบไม่ใช่เจ้าของห้อง แม้เป็นผู้ส่งคำขอเองก็ตอบแทนไม่ได้
- `404`: ไม่พบห้องหรือคำขอ
- `409`: ห้องตนเอง, มีคำขอ pending ซ้ำ, ห้องเต็ม/พักประกาศ, เป็นสมาชิกแล้ว,
  มีแมตช์เดิม หรือคำขอถูกตัดสินไปแล้ว
- `500`: ข้อผิดพลาดที่ไม่คาดคิด เช่น เขียนฐานข้อมูลไม่ได้ client ไม่ได้รับ stack trace/SQL

รายการ `mine` ต้องมีเฉพาะคำขอของบัญชีที่ล็อกอิน รายการ `owner` ต้องมีเฉพาะห้อง
ที่บัญชีนั้นเป็นเจ้าของ ไม่ส่ง email, phone, password hash หรือช่องทางติดต่อใน requester

## กฎและความถูกต้องของข้อมูล

- ห้ามขอเข้าห้องตัวเอง ห้อง inactive หรือห้องที่ไม่มีที่ว่าง
- คำขอ pending ไม่ใช่การจองที่ อาจมีหลายคนรอที่ว่างเดียวกัน
- ความจุรวมเจ้าของ: `ที่ว่าง = capacity - 1 - จำนวนสมาชิก approved`
- การส่งคำขอตรวจห้อง/สมาชิก/คำขอซ้ำและ INSERT ภายใน `BEGIN IMMEDIATE`
- การอนุมัติตรวจสิทธิ์ สถานะ และความจุอีกครั้งใน transaction เดียว แล้วจึง:
  1. เปลี่ยนคำขอเป็น approved และกำหนดเวลาตอบ
  2. เพิ่ม `ROOM_MEMBER`
  3. เพิ่ม `MATCHES` ระหว่างเจ้าของกับผู้ขอสำหรับห้องนั้น
  4. เปลี่ยนห้องเป็น full เมื่อครบความจุ (รวมถึง triggers เดิมของฐานข้อมูล)
- ถ้าขั้นตอนใดล้มเหลวต้อง rollback ทั้งหมด รวมถึงสถานะ full ที่เปลี่ยนจาก trigger
- การปฏิเสธไม่สร้างสมาชิกหรือแมตช์ และทำได้แม้ห้องเต็ม/พักประกาศแล้ว
- คำขอที่ตัดสินแล้วห้ามแก้ผล ถ้าถูกปฏิเสธผู้ขอส่งคำขอใหม่ได้เมื่อห้องยังรับอยู่
  โดยเก็บประวัติเดิมและใช้ `requestId` ใหม่
- ถ้าสองคำขอแย่งที่ว่างสุดท้าย อนุมัติได้เพียงคนเดียว อีกคำขอยังคง pending
  เจ้าของสามารถปฏิเสธคำขอที่เหลือได้ ระบบยังไม่ปฏิเสธให้อัตโนมัติ
- ไม่มีการยกเลิกคำขอ/คำขอแบบกลุ่มหรือ real-time polling ในฟีเจอร์นี้

## ทดสอบอัตโนมัติ

```bash
node --test tests/requests.test.mjs
npm test
npm run build
```

Tests ใช้ HTTP server จริงบนพอร์ตสุ่มและฐานข้อมูลแยก ไม่แตะฐานข้อมูลส่วนตัว
ครอบคลุม auth, การแยกบัญชี, การปลอม userId, คำขอซ้ำ, input ผิด,
อนุมัติ/ปฏิเสธ, ประวัติการส่งใหม่, ห้องเต็ม/พักประกาศ, สอง request แข่งกัน,
ฐานข้อมูลเขียนไม่ได้, trigger ล้มเหลวระหว่างอนุมัติ และหยุด/เปิด API ใหม่กับ SQLite เดิม
การทดสอบ concurrency นี้เป็นคำขอพร้อมกันใน Node process เดียว ไม่ใช่ load test หลายเครื่อง

## Checklist ให้เจ้าของฟีเจอร์ลองผ่านเว็บก่อน commit

1. เปิดเว็บด้วย `npm run dev` ตาม README ใช้บัญชีเจ้าของห้อง A และผู้ขอ B
   ใน browser profile แยกกันหรือ private window
2. B เปิดห้องที่มีที่ว่าง แล้วกดขอเข้าพัก ปุ่มต้องกลายเป็นรอพิจารณา
3. B เปิดหน้าคำขอเข้าพักและ refresh ต้องเห็นรายการเดิม
4. A เปิดหน้าคำขอเข้าพัก/refresh แล้วอนุมัติ ตรวจว่า B เป็นสมาชิกและที่ว่างลดลง
5. ทดลองอีกห้องแล้วปฏิเสธ ต้องไม่มีสมาชิก/แมตช์จากคำขอนั้น
6. B ลองส่งใหม่หลังถูกปฏิเสธ ต้องมีรายการใหม่โดยประวัติเดิมยังอยู่
7. ทดสอบหน้าจอ desktop/mobile และลองคำขอมากกว่าที่ว่างของห้อง

การตรวจรอบนี้รัน API tests และ build; ไม่มีเครื่องมือควบคุม browser ให้ใช้ใน session นี้
จึงไม่อ้างว่ากด UI ตาม checklist ข้างต้นแล้ว ต้องตรวจหน้าจอจริงก่อนส่งงาน

ไม่มีการ commit, push, เปลี่ยน branch, แก้ migrations หรือย้ายงานของเพื่อนเข้ามาในรอบนี้
เจ้าของฟีเจอร์ตรวจ diff และเป็นผู้ commit เองเมื่อพร้อม
