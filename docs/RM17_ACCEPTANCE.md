## สภาพแวดล้อมและบัญชี

- เตรียมบัญชีผ่าน registration/profile API แล้ว login/logout และทำรายการผ่าน browser จริง

- ทั้งสามมี LINE, Instagram, email และเบอร์จำลอง เพื่อพิสูจน์ว่าฟิลด์ถูกซ่อนจริงก่อนตอบรับ ไม่ใช่เพียงไม่มีข้อมูล

- ตรวจ desktop 1440×900, tablet 820×1000 และ mobile 390×844 / 320×740
- ใช้ browser เดียวสลับบัญชีด้วย logout/login; การแข่งตอบ/ถอนพร้อมกันตรวจด้วย HTTP tests เดิม
- Fault injection, signing key, token, รหัสผ่าน, SQLite และ screenshots อยู่ในพื้นที่ QA ชั่วคราว ไม่เก็บใน Git

## สิทธิ์ที่ตรวจยืนยัน

| บทบาท | ตอบรับ/ปฏิเสธ pending | ถอน pending | ข้อมูลติดต่อของอีกฝ่าย |
| --- | --- | --- | --- |
| ผู้ส่ง | ไม่ได้: API 403 และ UI ไม่มีปุ่มตอบแทนผู้รับ | ได้ หลังยืนยัน | เห็นเฉพาะเมื่อ accepted และคู่ยัง active |
| ผู้รับ | ได้ | ไม่ได้: API 403 และ UI ไม่มีปุ่มถอนแทนผู้ส่ง | เห็นเฉพาะเมื่อ accepted และคู่ยัง active |
| บัญชีที่สาม | ไม่ได้: API 403 | ไม่ได้: API 403 | ไม่ได้รับข้อมูลติดต่อของคู่ที่ตนไม่ได้เป็นสมาชิก |
| ไม่มี session / บัญชี inactive | ใช้ API ไม่ได้: 401 | ใช้ API ไม่ได้: 401 | ไม่ได้รับข้อมูลจาก friend API |

- การตรวจ 403 ใช้ ID คำชวนที่มีอยู่จริง ไม่ใช่อาศัย 404 ของ ID ที่ไม่มีอยู่
- ไม่เชื่อ `senderId`, `status` ที่แนบตอนส่ง หรือ `userId` ใน query เพื่อกำหนดผู้ใช้แทน token
- `accepted`/`declined` เปลี่ยนคำตอบหรือถอนไม่ได้; `cancelled` ถอนซ้ำได้เฉพาะผู้ส่ง โดยคงเวลาเดิม
- คู่ที่เคยปฏิเสธหรือถอนแล้วส่งซ้ำทั้งทิศเดิมและกลับด้านไม่ได้ตามกฎปัจจุบัน

## ความถูกต้องและการคงข้อมูล

ปลายทางมี FRIEND_CONNECTION เพียง 3 แถว ไม่มีคู่กลับด้านซ้ำ:

1. เอ → บี: `accepted`
2. เอ → ซี: `declined`
3. บี → ซี: `cancelled`

ทุกแถวมี respondedAt และเปรียบเทียบทุกฟิลด์รวม timestamps ก่อน/หลัง restart แล้วตรงกัน
ก่อนเริ่ม flow บันทึก snapshot USER, LIFESTYLE, PREFERENCE, ROOM, ROOM_IMAGE,
ROOM_REQUEST, ROOM_MEMBER, MATCHES และ ROOM_FAVORITE แล้วเทียบหลังจบ
โดยคืน fixture บัญชี inactive และ updated_at ที่ trigger เปลี่ยนจากการจำลองนั้นก่อนเทียบ
ตารางเดิมตรงกับ baseline; ห้องของซียัง available มีที่ว่าง 2 และไม่มีคำขอ สมาชิก หรือ room match เพิ่ม
`PRAGMA foreign_key_check` ไม่มีข้อผิดพลาด

## ให้ทีมทดสอบซ้ำ

1. เปิดฐาน QA **ใหม่** ตาม [วิธีเปิดเว็บแยกใน RM-16](RM16_ACCEPTANCE.md#วิธีให้ทีมทดสอบซ้ำอย่างปลอดภัย)
   ใช้ temporary directory ใหม่ ไม่ใช้ไฟล์ฐานข้อมูลเดิมของตัวเอง พอร์ตในตัวอย่างนั้นคือ 4349
2. สร้างบัญชีจำลองเอ/บี/ซี ใส่ช่องทางติดต่อที่ระบุได้ว่าเป็นข้อมูลทดสอบ เลือกรหัส QA ของตัวเอง
3. เอส่งบี ตรวจ pending และโปรไฟล์จากผู้ส่ง/ผู้รับ จากนั้นบีตอบรับ ตรวจ contact ทั้งสองฝั่ง
4. ซีค้นเอ/บีและดูโปรไฟล์ก่อนส่งคำชวน ต้องไม่เห็น contact ของคู่เอ–บี
5. เอส่งซี → ซีปฏิเสธ; บีส่งซี → เปิดถอนแล้วกดยกเลิกก่อน → ถอนจริง
6. ตรวจประวัติและโปรไฟล์ทั้งสามสถานะ รวมส่งซ้ำ เปลี่ยนผล และคัดลอก LINE
7. กดค้นหาห้องด้วยกันจากคู่ accepted ต้องไม่จองห้องหรือเพิ่มสมาชิกให้อัตโนมัติ
8. Refresh `/friends?view=friends` และ `/friends?view=invitations&invitations=history`
   จากนั้น restart API กับ QA directory เดิมแล้วตรวจครบทั้ง 3 บัญชีอีกครั้ง
9. ตรวจ desktop/tablet/mobile และใช้ HTTP tests สำหรับสิทธิ์ที่ UI ไม่เปิดปุ่มให้กด/ฐานข้อมูลล้มเหลว

```bash
node --test tests/friends.test.mjs tests/friend-discovery.test.mjs tests/friend-cancellation-api.test.mjs
npm test
npm run build
```
