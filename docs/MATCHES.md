# สมาชิกห้องและแมตช์ — โมดูลที่ 3 / ฟีเจอร์ที่สอง

## เชื่อมงานกับทีม — RM-24

เริ่มจาก [คำขอที่เจ้าของอนุมัติ](REQUESTS.md) จึงมีสมาชิกและ room match
การตอบรับ [คำชวนเพื่อน](FRIENDS.md) เพียงอย่างเดียวยังไม่สร้างข้อมูลชุดนี้

| หน้าที่ใน frontend | Adapter เดิม | หมายเหตุ |
| --- | --- | --- |
| อ่านแมตช์ของบัญชีปัจจุบัน | `api.matches()` | API คืน `{ matches }`; adapter คืน array และแปลง ID เป็น string |
| อ่านสมาชิกห้อง | `api.roomMembers(roomId)` | API คืนสมาชิกแบบ flat; adapter วางข้อมูลผู้ใช้ใน `member.user` |
| อ่านสถานะห้องหลังเปลี่ยนสมาชิก | `api.room(roomId)` | อย่าคำนวณที่ว่างจากแมตช์หรือประวัติคำขอ |
| ออกจากห้อง | `api.leaveRoom(roomId)` | ต้องยืนยัน และโหลดข้อมูลห้อง/แมตช์ใหม่หลังสำเร็จ |

ใช้ [ตัวแปร curl](REQUESTS.md#curl-setup) เดิม โดย RM_APPLICANT_TOKEN ต้องเป็นสมาชิก
ที่อนุมัติแล้วสำหรับตัวอย่างอ่านสมาชิก/ออกจากห้อง ทุก endpoint ต้องมี bearer token
ข้อมูล JSON ตัวอย่างด้านล่างเป็น response ดิบจาก API ไม่ใช่รูปร่างหลังผ่าน adapter

## API contract

### GET /api/rooms/:roomId/members

ต้องล็อกอิน และเป็นเจ้าของห้องหรือสมาชิกสถานะ `approved` ของห้องนั้น
ผู้ที่รออนุมัติ ถูกปฏิเสธ เป็นสมาชิกห้องอื่น หรือออกไปแล้ว ไม่มีสิทธิ์ดูรายการนี้

ผลสำเร็จ: `200 { "members": [...] }` แต่ละรายการมีเพียง:

- `userId`, `firstName`, `lastName`, `profileImage`
- `status`: `owner` หรือ `approved`
- `joinedAt`: ISO 8601 UTC เช่น `2026-11-12T03:00:00.000Z`

แสดงเจ้าของก่อนหนึ่งครั้ง ตามด้วยสมาชิกเรียงเวลาที่เข้าห้องและ `userId`
ห้องที่ยังไม่มีผู้ได้รับอนุมัติยังคืนเจ้าของ 1 คน ไม่ใช่ array ว่าง
เจ้าของยังเก็บใน `ROOM.owner_id` ไม่เพิ่มแถวซ้ำลง `ROOM_MEMBER`
ไม่คืน email, phone, วันเกิด, password hash หรือช่องทางติดต่อในรายการสมาชิก

Errors: `400` สำหรับ roomId ไม่เป็นจำนวนเต็มบวกที่ปลอดภัย,
`401` เมื่อไม่มีสิทธิ์ล็อกอิน, `403` เมื่อไม่ใช่เจ้าของ/สมาชิก,
`404` เมื่อไม่พบห้อง และ `500` สำหรับข้อผิดพลาดฐานข้อมูลที่ไม่คาดคิด
ทุก error เป็น `{ "error": "ข้อความ" }` ไม่คืน SQL หรือ stack trace

```bash
curl -sS "$RM_API/rooms/$RM_ROOM_ID/members" \
  -H "Authorization: Bearer $RM_APPLICANT_TOKEN"
```

ตัวอย่าง `200` สำหรับห้องความจุ 2 ที่อนุมัติเอแล้ว (สมาชิกเป็น flat object ไม่มี key `user`):

```json
{
  "members": [
    { "userId": 1, "firstName": "เจ้าของ", "lastName": "ทดสอบ", "profileImage": null, "status": "owner", "joinedAt": "2026-11-15T09:00:00.000Z" },
    { "userId": 2, "firstName": "เอ", "lastName": "ทดสอบ", "profileImage": null, "status": "approved", "joinedAt": "2026-11-15T10:00:00.000Z" }
  ]
}
```

`members.length` รวมเจ้าของ แต่ `room.memberCount` ไม่รวมเจ้าของ
เช่นห้องตัวอย่างมี `members.length = 2`, `memberCount = 1`, `availableSlots = 0`

### GET /api/matches

ต้องล็อกอิน ผลสำเร็จ: `200 { "matches": [...] }` ไม่มีแมตช์ให้คืน array ว่าง
แต่ละรายการคงรูปแบบเดิม:

- `matchId`, `matchedAt`
- `otherRole`: `owner` หรือ `member` สำหรับผู้ใช้ฝั่งตรงข้าม
- `room: { roomId, title }`
- `otherUser: { userId, firstName, lastName, profileImage, bio, lineId, instagram }`
- เพิ่ม `otherUser.phone` เป็นช่องทางสำรอง เฉพาะเมื่อไม่มีทั้ง LINE และ Instagram
  และมีเบอร์โทรในโปรไฟล์จริง (ค่าว่างหรือช่องว่างล้วนไม่นับเป็นข้อมูลติดต่อ)
  ถ้ามี LINE หรือ Instagram อยู่แล้ว จะไม่ส่งฟิลด์ `phone` เพิ่ม

หน้าแมตช์แสดงเบอร์สำรองด้วยส่วนช่องทางติดต่อเดิม หากไม่มีช่องทางใดเลยจะแสดง
“ยังไม่ได้เพิ่มช่องทางติดต่อ” โดยไม่สร้างเบอร์สมมติ ไม่เพิ่มคอลัมน์หรือ migration
สิทธิ์ยังเป็นเจ้าของกับสมาชิกที่อนุมัติในแมตช์นั้นเท่านั้น คนนอก ผู้รออนุมัติ
ผู้ถูกปฏิเสธ และสมาชิกที่ออกจากห้องแล้ว ไม่ได้รับเบอร์ผ่านแมตช์
รายการสมาชิกและโปรไฟล์สาธารณะยังไม่เปิดเผยเบอร์โทร

แมตช์ต้องเกี่ยวกับผู้ใช้ที่ล็อกอินเท่านั้น ไม่รับ `userId` ใน query เพื่อเลือกดูคนอื่น
เจ้าของเห็นผู้ที่ได้รับอนุมัติ ส่วนผู้เข้าพักเห็นเจ้าของเป็น `otherUser`
ไม่ใช่การจับคู่สมาชิกทุกคนกับทุกคนในห้อง และไม่ใช่คำชวนใน `FRIEND_CONNECTION`
เรียง `matchedAt` ล่าสุดก่อน และใช้ `matchId` มากก่อนเมื่อเวลาตรงกัน

คืนเฉพาะแมตช์ที่ completer ยังมี `ROOM_MEMBER.status = 'approved'` และ initiator
ยังเป็นเจ้าของห้องนั้น เพื่อไม่ให้แมตช์เก่าเปิดเผยช่องทางติดต่อหลังพ้นสถานะสมาชิก
แถวประวัติ `MATCHES` ไม่ถูกลบโดยการอ่าน หากบัญชีไม่มีสิทธิ์ล็อกอินตอบ `401`
และฐานข้อมูลล้มเหลวตอบ `500` แบบทั่วไป

```bash
curl -sS "$RM_API/matches" -H "Authorization: Bearer $RM_APPLICANT_TOKEN"
```

ตัวอย่าง `200` ฝั่งผู้ขอเมื่อเจ้าของมี LINE/Instagram:

```json
{
  "matches": [{
    "matchId": 7,
    "matchedAt": "2026-11-15T10:00:00.000Z",
    "otherRole": "owner",
    "room": { "roomId": 10, "title": "ห้องทดสอบ" },
    "otherUser": {
      "userId": 1, "firstName": "เจ้าของ", "lastName": "ทดสอบ", "profileImage": null,
      "bio": null, "lineId": "qa_owner", "instagram": "qa.owner"
    }
  }]
}
```

ถ้าเจ้าของอ่านรายการเดียวกัน `otherRole` จะเป็น `member` และ otherUser คือผู้ขอ
หากคู่มีแต่เบอร์ จะมี key `phone` เพิ่มตามกฎสำรองข้างต้น แต่ endpoint นี้ไม่ส่ง email
ต่างจาก friend connection ที่ accepted ซึ่งส่งช่องทางติดต่อที่อนุญาตทั้ง 4 ฟิลด์

### DELETE /api/rooms/:roomId/members/me

เฉพาะสมาชิก approved หรือสมาชิกเดิม left ของห้องนั้น เจ้าของต้องจัดการประกาศแทน
ไม่รับ userId เพื่อออกแทนคนอื่น และไม่ต้องมี body:

```bash
curl -sS -X DELETE "$RM_API/rooms/$RM_ROOM_ID/members/me" \
  -H "Authorization: Bearer $RM_APPLICANT_TOKEN"
```

ผลสำเร็จ `200 { "success": true }`; adapter ไม่คืนข้อมูลที่ต้องใช้ต่อ ให้โหลดห้องและแมตช์ใหม่
API ตั้ง ROOM_MEMBER เป็น `left` คืนที่ว่างและเปิดห้อง full ให้ available หากยังรับอยู่
ห้อง inactive ยังคง inactive ส่วน ROOM_REQUEST ที่อนุมัติและ MATCHES ยังคงเป็นประวัติ
สมาชิกที่ออกแล้วไม่ได้รายชื่อสมาชิก/ช่องทางติดต่อผ่านแมตช์ และหากกลับต้องส่งคำขอใหม่ให้เจ้าของอนุมัติ
การออกซ้ำโดยบัญชีเดิมที่เป็น left แล้วคืนผลสำเร็จเดิมโดยไม่เปลี่ยน joinedAt

Errors: `400` ID ผิด, `401` session ใช้ไม่ได้, `403` เจ้าของ/คนนอก/ผู้ที่ไม่เคยเป็นสมาชิก,
`404` ไม่พบห้อง และ `500` เมื่อฐานข้อมูลล้มเหลว โดย rollback ก่อนตอบ error

## สิทธิ์ในรายละเอียดห้อง

ก่อนแก้ `GET /api/rooms/:roomId` คืนสมาชิกให้คนนอกได้ แม้ `/members` ปฏิเสธไว้
ตอนนี้ใช้กฎเดียวกันทั้งสองทาง:

- เจ้าของ/สมาชิก approved: `room.members` มีสมาชิก approved โดยไม่ซ้ำเจ้าของ
- บุคคลทั่วไป/ผู้รอ/ผู้ถูกปฏิเสธ/สมาชิกที่ออก: `room.members` เป็น `[]`
- ข้อมูลเจ้าของประกาศพื้นฐานและจำนวนที่ว่างยังดูได้ตามเดิม
- `room.memberCount` นับเฉพาะสมาชิกที่อนุมัติ ไม่รวมเจ้าของ
  ต่างจากจำนวนรายการใน `/members` ที่รวมเจ้าของด้วย

การพักประกาศ `inactive` ไม่ได้ทำให้สมาชิกเดิมออกจากห้อง จึงยังดูสมาชิกและแมตช์ได้
การลบห้องใช้ cascade เดิม ไม่เหลือสมาชิกหรือแมตช์ชี้ไปห้องที่ไม่มีอยู่

## ทดสอบ

```bash
node --test tests/matches.test.mjs
npm test
npm run build
```

Tests เปิด HTTP server จริงบนพอร์ตสุ่มและใช้ SQLite แยกจากข้อมูลส่วนตัว
ตรวจ auth/ID, empty state, pending/rejected/outsider, ช่องทางข้อมูลผ่านรายละเอียดห้อง,
field whitelist, ลำดับเจ้าของและ timezone เก่า, การแยกแมตช์รายบัญชี,
สมาชิกออก, พัก/ลบห้อง, ฐานข้อมูลล้มเหลว, บัญชี inactive และ persistence หลัง restart
เคสเดิมจำลองสมาชิกออกผ่านฐานข้อมูล ส่วน `tests/ux-lifecycle.test.mjs` ตรวจ
`DELETE /api/rooms/:roomId/members/me` จริง รวมสิทธิ์/idempotency/failure/rejoin/persistence
การอ่านต้องไม่เปลี่ยนข้อมูล ตรวจ snapshot และทดสอบได้แม้ SQLite อยู่ใน query-only mode

ก่อน commit ให้ลองผ่านเว็บด้วยบัญชีเจ้าของ สมาชิก และคนนอก:

1. หลังอนุมัติ เปิดหน้าเพื่อนร่วมห้องและ refresh ยังต้องเห็นแมตช์เดิม
2. เจ้าของเห็นผู้เข้าพัก ผู้เข้าพักเห็นเจ้าของ พร้อมจำนวนสมาชิกที่รวมเจ้าของ
3. กดดูห้องและสมาชิก ตรวจชื่อ/รูปและลิงก์กลับห้อง
4. บัญชีที่ไม่ได้รับอนุมัติต้องไม่มีแมตช์นั้น และไม่ได้รายชื่อสมาชิกผ่าน API รายละเอียดห้อง
5. ตรวจหน้า empty/error และ desktop/mobile ของ frontend ที่มีอยู่

ผลตรวจรับเจ้าของกับผู้ขอ 2 คน รวมออกจากห้อง/สมัครใหม่/อนุมัติซ้ำและ restart อยู่ใน
[RM-16 acceptance](RM16_ACCEPTANCE.md) ส่วนประวัติการปรับ UX อยู่ใน [UX_FIXES.md](UX_FIXES.md)

## RM-14 — เบอร์โทรสำรอง

  ค่าว่าง/ช่องว่าง/ไม่มีเบอร์, คนนอก/ผู้รอ/ผู้ถูกปฏิเสธ/สมาชิกห้องอื่น,

  สมาชิกเห็นเบอร์เจ้าของ, ไม่มีช่องทางติดต่อ, มี LINE แล้วซ่อนเบอร์,

- ตรวจ desktop 1440×900, tablet 820×1000 และ mobile 320×740 โดยเบอร์ไม่ล้น
- `npm test` ผ่าน 111 ข้อ; `npm run build` และ `git diff --check` ผ่าน
- งานนี้ไม่แก้ schema หรือเพิ่ม migration; การแยก error สมาชิกแต่ละห้องอยู่ใน RM-15 ด้านล่าง

## RM-15 — โหลดสมาชิกและลองใหม่แยกแต่ละห้อง

- แสดงรายการแมตช์ทันทีที่ `/api/matches` สำเร็จ จากนั้นโหลดสมาชิกแต่ละห้องแยกกัน
  ห้องหนึ่งช้าหรือล้มเหลวไม่ทำให้แมตช์และห้องอื่นหายไป
- แต่ละห้องมี loading, empty และ error ของตัวเอง ปุ่มลองใหม่เรียกเฉพาะ
  `/api/rooms/:id/members` ของห้องนั้น ไม่โหลดแมตช์หรือสมาชิกห้องอื่นซ้ำ
- หลายการ์ดที่อยู่ห้องเดียวกันใช้ผลการโหลดร่วมกัน และเรียก API หนึ่งครั้งต่อห้อง
- ข้อผิดพลาดของ `/api/matches` ใช้สถานะและปุ่มลองใหม่ระดับหน้าแยกต่างหาก
- ถ้า member API ตอบ 401/403/404 จะซ่อนช่องทางติดต่อที่เคยโหลดของห้องนั้น
  รวมถึงระหว่างลองใหม่และหลังลองใหม่ล้มเหลว มีปุ่มอัปเดตรายการแมตช์เพื่อตรวจสิทธิ์ล่าสุด
- ไม่ใช้ response เก่าหลังออกจากหน้า/เริ่มโหลดชุดใหม่ คืนโฟกัสไปผลลัพธ์หลังลองใหม่
  แต่ไม่แย่งโฟกัสหากผู้ใช้ย้ายไปใช้ปุ่มอื่นระหว่างรอ
- ใช้ `src/pages/MatchesPage.css` เฉพาะหน้านี้ ไม่เปลี่ยน API หรือฐานข้อมูล

ตรวจผ่าน browser ด้วย SQLite แยก: ห้องหนึ่ง 503/อีกห้องล่าช้า, retry ล้มเหลวและ
สำเร็จ, สมาชิกว่าง, รายการแมตช์ล้มเหลวแล้ว retry, refresh, ย้ายหน้าในระหว่างโหลด,
