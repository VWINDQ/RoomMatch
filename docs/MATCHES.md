# สมาชิกห้องและแมตช์ — โมดูลที่ 3 / ฟีเจอร์ที่สอง

## ขอบเขตและไฟล์

ต่อยอดจากการอนุมัติคำขอเข้าพักเดิม โดยแยก API อ่านสมาชิก/แมตช์มาไว้ใน
`server/matches.js` คง URL และชื่อฟิลด์เดิม ส่วนการปรับ UX ล่าสุดเพิ่ม endpoint
ออกจากห้องพร้อม UI ยืนยัน ดูรายละเอียด [UX_FIXES.md](UX_FIXES.md)

ไฟล์ในงานนี้:

- `server/matches.js`: ตรวจสิทธิ์ อ่านสมาชิก และอ่านแมตช์ที่ยังมีสมาชิกอยู่จริง
- `server/app.js`: เชื่อมโมดูล และใช้สิทธิ์เดียวกันกับรายชื่อสมาชิกในรายละเอียดห้อง
- `tests/matches.test.mjs`: HTTP integration tests กับฐานข้อมูลทดสอบแยก
- `docs/MATCHES.md`, `docs/ARCHITECTURE.md`, `README.md`: เอกสารการทำงานและวิธีทดสอบ

## API contract

### GET /api/rooms/:roomId/members

ต้องล็อกอิน และเป็นเจ้าของห้องหรือสมาชิกสถานะ `approved` ของห้องนั้น
ผู้ที่รออนุมัติ ถูกปฏิเสธ เป็นสมาชิกห้องอื่น หรือออกไปแล้ว ไม่มีสิทธิ์ดูรายการนี้

ผลสำเร็จ: `200 { "members": [...] }` แต่ละรายการมีเพียง:

- `userId`, `firstName`, `lastName`, `profileImage`
- `status`: `owner` หรือ `approved`
- `joinedAt`: ISO 8601 UTC เช่น `2026-11-12T03:00:00.000Z`

แสดงเจ้าของก่อนหนึ่งครั้ง ตามด้วยสมาชิกเรียงเวลาที่เข้าห้องและ `userId`
ห้องที่ยังไม่มีผู้ได้รับอนุมัติยังคืนเจ้าของ 1 คน ไม่ใช่ array ว่าง
เจ้าของยังเก็บใน `ROOM.owner_id` ไม่เพิ่มแถวซ้ำลง `ROOM_MEMBER`
ไม่คืน email, phone, วันเกิด, password hash หรือช่องทางติดต่อในรายการสมาชิก

Errors: `400` สำหรับ roomId ไม่เป็นจำนวนเต็มบวกที่ปลอดภัย,
`401` เมื่อไม่มีสิทธิ์ล็อกอิน, `403` เมื่อไม่ใช่เจ้าของ/สมาชิก,
`404` เมื่อไม่พบห้อง และ `500` สำหรับข้อผิดพลาดฐานข้อมูลที่ไม่คาดคิด
ทุก error เป็น `{ "error": "ข้อความ" }` ไม่คืน SQL หรือ stack trace

### GET /api/matches

ต้องล็อกอิน ผลสำเร็จ: `200 { "matches": [...] }` ไม่มีแมตช์ให้คืน array ว่าง
แต่ละรายการคงรูปแบบเดิม:

- `matchId`, `matchedAt`
- `otherRole`: `owner` หรือ `member` สำหรับผู้ใช้ฝั่งตรงข้าม
- `room: { roomId, title }`
- `otherUser: { userId, firstName, lastName, profileImage, bio, lineId, instagram }`

แมตช์ต้องเกี่ยวกับผู้ใช้ที่ล็อกอินเท่านั้น ไม่รับ `userId` ใน query เพื่อเลือกดูคนอื่น
เจ้าของเห็นผู้ที่ได้รับอนุมัติ ส่วนผู้เข้าพักเห็นเจ้าของเป็น `otherUser`
ไม่ใช่การจับคู่สมาชิกทุกคนกับทุกคนในห้อง และไม่ใช่คำชวนใน `FRIEND_CONNECTION`
เรียง `matchedAt` ล่าสุดก่อน และใช้ `matchId` มากก่อนเมื่อเวลาตรงกัน

คืนเฉพาะแมตช์ที่ completer ยังมี `ROOM_MEMBER.status = 'approved'` และ initiator
ยังเป็นเจ้าของห้องนั้น เพื่อไม่ให้แมตช์เก่าเปิดเผยช่องทางติดต่อหลังพ้นสถานะสมาชิก
แถวประวัติ `MATCHES` ไม่ถูกลบโดยการอ่าน หากบัญชีไม่มีสิทธิ์ล็อกอินตอบ `401`
และฐานข้อมูลล้มเหลวตอบ `500` แบบทั่วไป

## สิทธิ์ในรายละเอียดห้อง

ก่อนแก้ `GET /api/rooms/:roomId` คืนสมาชิกให้คนนอกได้ แม้ `/members` ปฏิเสธไว้
ตอนนี้ใช้กฎเดียวกันทั้งสองทาง:

- เจ้าของ/สมาชิก approved: `room.members` มีสมาชิก approved โดยไม่ซ้ำเจ้าของ
- บุคคลทั่วไป/ผู้รอ/ผู้ถูกปฏิเสธ/สมาชิกที่ออก: `room.members` เป็น `[]`
- ข้อมูลเจ้าของประกาศพื้นฐานและจำนวนที่ว่างยังดูได้ตามเดิม
- `room.memberCount` นับเฉพาะสมาชิกที่อนุมัติ ไม่รวมเจ้าของ
  ต่างจากจำนวนรายการใน `/members` ที่รวมเจ้าของด้วย

การพักประกาศ `inactive` ไม่ได้ทำให้สมาชิกเดิมออกจากห้อง จึงยังดูสมาชิกและแมตช์ได้
การลบห้องใช้ cascade เดิม ไม่เหลือสมาชิกหรือแมตช์ชี้ไปห้องที่ไม่มีอยู่

## ทดสอบ

```bash
node --test tests/matches.test.mjs
npm test
npm run build
```

Tests เปิด HTTP server จริงบนพอร์ตสุ่มและใช้ SQLite แยกจากข้อมูลส่วนตัว
ตรวจ auth/ID, empty state, pending/rejected/outsider, ช่องทางข้อมูลผ่านรายละเอียดห้อง,
field whitelist, ลำดับเจ้าของและ timezone เก่า, การแยกแมตช์รายบัญชี,
สมาชิกออก, พัก/ลบห้อง, ฐานข้อมูลล้มเหลว, บัญชี inactive และ persistence หลัง restart
เคสเดิมจำลองสมาชิกออกผ่านฐานข้อมูล ส่วน `tests/ux-lifecycle.test.mjs` ตรวจ
`DELETE /api/rooms/:roomId/members/me` จริง รวมสิทธิ์/idempotency/failure/rejoin/persistence
การอ่านต้องไม่เปลี่ยนข้อมูล ตรวจ snapshot และทดสอบได้แม้ SQLite อยู่ใน query-only mode

ก่อน commit ให้ลองผ่านเว็บด้วยบัญชีเจ้าของ สมาชิก และคนนอก:

1. หลังอนุมัติ เปิดหน้าเพื่อนร่วมห้องและ refresh ยังต้องเห็นแมตช์เดิม
2. เจ้าของเห็นผู้เข้าพัก ผู้เข้าพักเห็นเจ้าของ พร้อมจำนวนสมาชิกที่รวมเจ้าของ
3. กดดูห้องและสมาชิก ตรวจชื่อ/รูปและลิงก์กลับห้อง
4. บัญชีที่ไม่ได้รับอนุมัติต้องไม่มีแมตช์นั้น และไม่ได้รายชื่อสมาชิกผ่าน API รายละเอียดห้อง
5. ตรวจหน้า empty/error และ desktop/mobile ของ frontend ที่มีอยู่

การตรวจ browser และ API ล่าสุด รวมออกจากห้อง/สมัครใหม่/อนุมัติซ้ำ อยู่ใน
[UX_FIXES.md](UX_FIXES.md) ไม่มีการ stage, commit หรือ push ให้
